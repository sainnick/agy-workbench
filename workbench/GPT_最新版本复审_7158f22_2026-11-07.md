## 二、最新代码仍有四个值得优先处理的缺口


## 1. P1｜一次性票据不是不可伪造的执行凭据
查看票据核验代码目前验收身份由 jobs/tickets/*.json、任务文件和 delegations.jsonl 共同决定。这确实堵住了旧版通过 --engine=review 直接跳过验收的漏洞。但票据和账本依然是普通本地文件。如果 AGY 与验收器共享同一 macOS 用户的文件写入权限，AGY 仍可能篡改这些证据。还有一个与你截图直接相关的缺口：proof.mjs 第 244–249 行的身份声明检测只覆盖有限的表达方式，不能可靠识别所有“我已经调用 Claude”的说法。结论：防误报机制明显加强，但尚未实现独立可信的身份鉴别。

## 2. P1｜本地工作台仍没有独立控制 Token
查看 HTTP 接口新代码添加了 Host 校验，却没有实现之前要求的写操作控制令牌。本机其他进程仍可直接请求 /api/send 和 /api/project/:id。对于有权指挥多个 Agent 的工作台，这是需要补齐的控制边界。

## 3. P1｜发送附件失败时，用户可能先收到成功说明
查看发送顺序现在的实际流程是：发送正文（可能已经包含验收通过标记）逐个上传附件全部成功后才正式记账这个顺序改善了附件说明被吞的问题，但如果附件上传失败，微信里已经发出的正文不会被撤回。用户可能看到“已核验”的说明，却没有收到完整交付物。建议增加“部分发送成功”的状态，并且只有全部附件送达后才发送最终交付确认。

## 4. P1｜承诺核销尚未实现强制任务绑定
查看核销逻辑新版已经从“同一窗口所有承诺一起兑现”，改成了优先任务 ID、匹配分数和最近一条承诺的核销方式，改进很大。但实际微信发送链路仍然没有向核销函数稳定传入明确的任务 ID 和发送消息 ID，因此在无法匹配时，仍有可能用一份不相关的回执结清另一项承诺。这里应该继续收紧为：找不到明确的任务关联，就保持待核验，不自动结清。

## 三、两个尚未完成的工程环节
微信异常处理现在会重试并存死信，不过重试耗尽后仍会将消息标记为已处理。因此，它是“失败可追踪、可人工补发”，还不是自动恢复的可靠队列。另外，仓库虽然新增了编译产物和 package-lock.json，但没有看到配套的 GitHub Actions 工作流和针对这些新加固逻辑的完整自动化测试。仓库里的“Claude 加固完成报告”描述了本机测试，也明确承认尚未进行真实微信发送故障注入。查看加固报告这份报告自称由 Claude Code Opus 5.5 执行，但文件署名本身不能作为模型调用真实性的独立证明。
